## 1. 这是什么

一套**高速公路入口（MTC 车道）自动发卡机器人**的车道控制软件，加一台**机器人模拟器**。

- `lanectl/` —— 车道控制上位机（Qt Widgets）：选工位、写卡、送卡、控制语音屏和栏杆、记录通行流水
- `lanesim/` —— 机器人模拟器（控制台）：4 个工位 + 卡箱 + 伸缩机构 + 读卡 + 语音屏 + 栏杆

有了模拟器，**不需要真机和真车就能把整条车道跑通、录 demo**。

## 2. 真实业务背景（为什么流程长这样）

入口车道沿车辆行进方向布置：

```
        ┌──────────── 车道 ────────────┐
  ══════╪══════════════════════════════╪══════
       [A]      发卡机器人(岛头)       [B]   栏杆
     触发线圈                          存在线圈
```

机器人本体是 **4 个工位**（对应现场的上左/上右/下左/下右），每个工位一套卡箱 + 读卡天线：

| 工位 | 位置 | 说明 |
|---|---|---|
| 1 | 上左 | 上组读卡器 m_handle1 |
| 2 | 上右 | 上组读卡器 m_handle2 |
| 3 | 下左 | 下组读卡器 m_handle3，**送卡前伸缩机构要伸出 20cm** |
| 4 | 下右 | 下组读卡器 m_handle4，同上 |

**最关键的一条：备卡是机器人自己维持的，车道不参与。**

这是看真实代码才发现的设计：机器人上电自检后就把 4 个工位各备一张卡，送完/回收后自动补备下一张；某个工位备卡失败，它会自动切到**配对工位**（上左↔上右、下左↔下右）重试一次，成功后主动上报事件通知车道"可以继续"。车道软件只管三件事：**选一个已备好卡的工位 → 写卡 → 送卡**。

一条车的完整流转：

```
上电 → 自检 → 4 工位各自备卡 (B4 上报卡号, B2 上报状态)
车压触发线圈 A  (B3 事件1)
  → 车道从 B2 里挑一个"已备卡"的工位
       ├ 没有 → 屏显"请稍候", 等 B2 出现可用工位再继续
       └ 有   → 写卡 (B1) → 送卡 (B1)
                  └ 下工位: 伸缩机构先伸 20cm
  → 屏显/语音 "请取卡"
司机取卡 (B3 事件3, 带工位号)
  → 屏显"卡已被取走，一路平安" + 语音 + 抬杆
  → 设备自动缩卡 + 自动补备该工位
车压存在线圈 B 离开 (B3 事件2) → 落杆 → 待车
```

异常分支：

| 场景 | 处理 |
|---|---|
| 某工位备卡失败 | 设备切配对工位重试 1 次；成功上报 `EV_PREPARE_RECOVER` |
| 4 个工位都不可用 | B2 上报"全部工位不可用"，车道屏显"请稍候"并报警 |
| 写卡失败 | 车道换一个工位重试 1 次，仍失败报故障 |
| 15s 未取卡 | 重播"请取卡" → 再 15s → 回收 |
| 未取卡驶离 | 立即回收 + 报警（不然下一辆会拿错卡） |
| 某工位卡箱空 | B3 事件6 + B2 状态变化，车道预警 |
| 心跳超时 45s | 报警（**脏点：只报不处理**） |

异常场景一条命令就能复现：

```powershell
.\bin\LaneSim.exe --bin 0            # 卡箱空, 看"无可用工位"
.\bin\LaneSim.exe --prep 1           # 备卡必失败 -> 配对工位重试 -> 全部不可用
.\bin\LaneSim.exe --fail 1           # 写卡必失败 -> 车道换工位重试 -> 报故障
```

## 6. 协议 v0（A 阶段）

```
+------+------+-----+-----+-----+---------+-----+
| 0xAA | 0x55 | LEN | SEQ | CMD | PAYLOAD | CHK |
+------+------+-----+-----+-----+---------+-----+
  LEN  payload 长度 (0~200, 超了静默截断)
  SEQ  发送序号 0~255 循环 —— 发出去, 但没人校验
  CHK  LEN..PAYLOAD 逐字节累加取低 8 位 —— 不是 CRC16
```

> 现场用的是 `FF … FF` 起止 + 转义（FE 01=FF, FE 00=FE）+ BCC。这里的 AA55 是自制帧，
> 替换留到 W4 协议层重构 —— 先把**业务**对齐，再动字节格式。

**上行（机器人 → 车道）**

| CMD | 名称 | payload | 对应现场 |
|---|---|---|---|
| 0xB1 | 执行结果 | `[1B 命令字][1B 结果码]` | B1 |
| 0xB2 | 状态 | `[1B 整体][4×(1B 工位状态,1B 卡数)]` = 9B | B2 |
| 0xB3 | 事件 | `[1B 事件码][1B 工位]` | B3 |
| 0xB4 | 备卡成功 | `[1B 工位][8B 卡号]` | — |
| 0xB5 | 来车数据 | `[8B 车牌][1B 车型]` | — |
| 0xA0 | 心跳 | `[1B 序号]`，每 20s 主动发 | — |

**下行（车道 → 机器人）**

| CMD | 名称 | payload |
|---|---|---|
| 0x01 | 自检 | 空 |
| 0x02 | 查状态 | 空（只回 B2） |
| 0x03 | 手动备卡 | `[1B 工位]`（正常由设备自己备） |
| 0x04 | 写卡 | `[1B 工位][40B 入口信息]` |
| 0x05 | 送卡 | `[1B 工位]` |
| 0x06 | 缩卡 | `[1B 工位]` |
| 0x07 | 回收 | `[1B 工位][1B 原因]` |
| 0x08 | 语音 | `[1B 语音号]` |
| 0x09 | 屏显 | `[1B 行号][N 文本]` |
| 0x0A | 栏杆 | `[1B 0落 1抬]` |
| 0x0B | 复位 | 空 |
| 0x0C | 调试 | `[1B 动作]` 1来车 2取卡 3驶离 4未取卡驶离 5清车道 |
| 0x0D | 时间同步 | `[14B yyyyMMddhhmmss]`（对应现场 C1） |

**工位状态**：0 空 / 1 已备卡 / 2 备卡失败·缺卡 / 3 已送卡 / 4 故障
**整体状态**：0 正常 / 1 部分工位不可用 / 2 全部不可用
**事件码**：1 来车 / 2 驶离 / 3 取卡 / 4 备卡恢复 / 5 未取卡驶离 / 6 工位缺卡 / 7 余量低 / 8 工位故障
**结果码**：0 成功 / 1 工位无卡 / 2 卡滞 / 3 写卡失败 / 4 回读校验失败 / 5 超时 / 6 状态不允许 / 7 未知命令 / 8 工位不存在 / 9 未备卡

**入口信息（40 字节定长）**：站号 4B + 车道 2B + 车型 1B + 车牌 8B + 时间 14B + 卡号 8B + 填充 3B

## 8. 已知 bug（是 bug，不是风格问题）

1. **车辆滞留会覆盖上一个流程**：车还没走又来一辆，`EV_CAR_ARRIVED` 直接重置 `m_cur`，上一辆流水消失。真实车道必须锁车道并报警。
2. **故障后必须人工救场**：`enterFault` 只是停下报警，车道那辆车还占着位。必须点[故障恢复]。
3. **恢复链用固定延时兜底**：复位完如果没有残留卡，就没有回收结果，靠 `singleShot(1200)` 硬等。
4. ~~**超时定时器不分命令**~~ → **W1 已修**：每条命令一个 waiter + 独立 deadline，超时能定位到具体命令字。
5. **断开连接不做收尾**：不落杆、不回收卡，设备还在等取卡。
6. **清流水可清掉正在跑的车**：`onClearFlow` 不判断 `m_cur`。
7. **坏帧即丢包**：`parseFrame` 返回 -1 后清空缓冲，半包会连带丢掉后面的完整帧。
8. **无可用工位时车已经进道了**：屏显"请稍候"，但没有引导车辆退出或转人工的逻辑。
9. **写卡换工位重试时没校验目标工位卡号**：`m_posCard` 为空时会写 `00000000`。
10. **心跳超时不落地当前流程**：只报警，`m_state` 还是"等待取卡"，实际设备已经掉线。

## 11. 用这份基线做面试素材

```powershell
git tag v0-dirty          # 基线
git log --oneline v0-dirty..HEAD
git diff --stat v0-dirty HEAD
```

能讲的三句话（重构后填真实数字）：

- 「基线的事件分发是两条 if/else 链，事件到了不校验状态，车辆滞留会覆盖上一辆的数据；改成状态表后非法事件统一报警，加一道工序只加一行。」
- 「工位选择原来写死 1→2→3→4，上一辆刚用的工位还没补备，下一辆就挑了别的，导致上下组负载不均；抽成策略后可以按剩余卡数和组负载轮转。」
- 「协议原来是两份拷贝，已经分叉出一个字段长度不一致的 bug；抽成共享库后这类问题不可能再出现。」
